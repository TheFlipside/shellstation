# Changelog

All notable changes to this project are documented in this file.

## Unreleased

### Added

- **Settings → Data Export / Import** (previously "Database — Export / Import") now also covers the client settings and the command bar buttons, which live in the webview's localStorage and were lost when a database was moved to another machine. **Export Data** opens a dialog with one checkbox each for **Database**, **Settings** and **Command buttons**, and writes the chosen ones into a single JSON file. **Import Data** reads the file first and offers only the sections it actually holds, so a full move to a new machine is a single import. Database import keeps its existing behaviour (rows that already exist are skipped). Settings overwrite the current values, each going through the same setter as the Settings dialog, so an invalid or unknown value is ignored rather than stored; an empty language ("follow the system") leaves the importing machine's language alone. Five safety settings — blocking private addresses, confirming multi-line pastes, confirming before quitting with open sessions and before closing a tab, and checking for updates — can be switched on by an import but never off, and three settings that make something happen with less care can be switched off but never on: paste on right-click, which types into a live session; copy on selection, which puts what the remote host printed on the clipboard for the next paste; and closing a tab when its session ends, which throws away what it showed. So a file from someone else cannot quietly weaken them; changing one the other way stays a deliberate change in Settings, even when the file is this machine's own export. Command buttons are added after the existing ones and never replace them: a button with the same id (in any letter case), or the same name and command, is skipped. Since a button types its command into a live session on one click, the import dialog lists every button the file would add with its command as written (runs of spaces collapsed, so padding cannot push the rest of a command out of view), says what a click does, and imports only on a click of **Import** — not on Enter, so a stray keystroke cannot skip the list. A button whose name or command holds control or format characters (zero-width, text-direction, tag characters), line separators, blank-looking characters or unusual spaces is refused, so it cannot look different from what it sends. Names keep emoji sequences and icon-font (private use) glyphs; commands, which never need them, also refuse private-use characters and variation selectors. Settings that belong to one machine (database connection, session and application logging) are not exported. Sections are imported independently, so a failed database import is reported without stopping the settings and buttons. The new strings, and the section's updated help text, are translated into all 14 UI languages.
- The new file is a versioned envelope (`format: "shellstation-export"`, `version: 1`, `app_version`, `exported_at`, and optional `database`, `settings` and `command_buttons` sections) written by the new `data_export_file` command, which replaces `db_export_file`. The command shows the save dialog itself instead of taking a path from the webview, so the file it writes is always one the user picked; only one export runs at a time, and the dialog title the webview supplies is capped. It writes through a temporary file that is then renamed into place, so a failed export never leaves a half-written file and a symlink at the target is replaced rather than followed, and it does the write on a blocking thread rather than an async worker. The backend checks the frontend-supplied sections before writing: settings must be a flat map of scalars (at most 64 entries, strings up to 256 characters) and buttons must match the command bar's own limits, with no id used twice. The import side applies the same entry limits before anything is imported. Database-only files written by earlier versions still import as before. A file from a newer format version is refused with a message to update instead of being half-read.
- The connection timeout, keepalive interval and keepalive count setters now accept only whole numbers within range (1–300 s, 0–3600 s and 1–100). The backend reads them as integers, so a fraction or an oversized value would otherwise be refused there; the Settings dialog only ever offered valid values. The backend now keeps these settings and checks the same ranges (see **Fixed**); it used to cap the timeout at 300 s silently, so a value above that, which only an imported file could set, is now ignored instead.
- **Settings → Import SecureCRT** now also brings over the buttons of SecureCRT's button bars and Command Manager, which users who move from SecureCRT had to build again by hand. The file is read first, by the new `inspect_securecrt` command, and a dialog like the one behind **Import Data** offers **Sessions**, **Button bars** and **Command Manager**. A part is offered only when the file has something in it that can be imported, and every button is listed with its command before anything is imported. Sessions are imported as before.
  - **Where the buttons go.** They are added to the command bar after the existing ones. A button already there with the same name and command is skipped, so one that is both on a bar and in the Command Manager (VanDyke's own way to move bars into the Command Manager copies them) is added once. All bars go into the one command bar. Buttons get the default color and pass the same hidden-character check as buttons from a ShellStation export file.
  - **What carries over.** Only Send String buttons, since a command bar button only sends text. A command carries over as SecureCRT wrote it: its send-string escapes (`\r`, `\n`, `\t`, `\b`, `\e`, `\p`, `\v`, `\\`) are the command bar's own, and so, from this version, are its three-digit octal codes for control characters (see **Changed**), so a Ctrl+C button (`\003`) keeps working. A printable character written as a code (`\101`) is written out as that character, so the import dialog shows the text a button types rather than digits that type it. Every converted command is read back the way the command bar reads it and compared with what SecureCRT sends; a button whose two differ is skipped. A comma in a command or label is written `\,` in the export and read as a comma. In a label, `&&` becomes `&` and a single `&`, which marks a Windows access key, is dropped. A label longer than 32 characters is shortened.
  - **What is skipped, with a warning after the import:** a button with another function (a menu function, a script, …) or with no label, one that sends nothing, one with an octal code above `\177`, which SecureCRT sends as a single raw byte and a command bar button, sending text, cannot, one whose codes, written out, would run into the characters around them (in `\0\061\062`, `\0` is no code, but `\012` would be a line feed), and one whose command is longer than 1024 characters, which is not shortened, since that would change what it sends. At most 1000 entries are taken from the button bars, and as many from the Command Manager; unassigned entries do not count. An entry over 64 KiB, far more than any importable button needs, is skipped before it is taken apart. A warning quotes at most 64 characters of a bar name, label or function, so a crafted file cannot multiply a long name into every warning on its bar.
  - The section picker of the data export and import dialogs is now shared with this dialog. A section can carry a second sentence as a line of its own, which the checkbox's description includes, and the button list shows a name cut short by the layout in full on hover.
- Tests: 25 Rust unit tests in `import/securecrt.rs` for the SecureCRT buttons and the parser fixes below (the export layout of SecureCRT 9.7 and 8.x, files without some of the blocks, Command Manager folders and their nesting limit, blocks nested or repeated, cut-off files, a `<string>` inside a `<string>`, the entry limit and unassigned entries, oversized entries, warnings quoting long bar, key and session names, field and label escaping, octal codes, the name and command limits, and each reason to skip a button), and `src/secureCrtImport.test.ts` and `src/components/SecureCrtImportDialog.test.tsx` (15 tests: ids, color and the hidden-character check, importing only the picked parts without duplicates or changes to existing buttons, and the dialog's sections, empty blocks, button lists and keyboard handling). Two tests in `src/components/CommandBar.test.tsx` cover the octal codes the command bar reads and those it sends as written, on the same edge cases as the import's tests, so the two scanners cannot drift apart unnoticed.
- Tests: 18 Rust unit tests in `commands/data_transfer.rs` (settings and button validation including duplicate ids, the empty-selection check, section omission, the database section reading back as `db_import` input, the temp-file write, the dialog title check and the one-export-at-a-time guard), and `src/dataTransfer.test.ts`, `src/stores/settingsStore.test.ts` and `src/components/DataTransferDialog.test.tsx` (87 tests: file parsing including legacy, malformed and oversized files, settings and button import rules including the direction each guarded setting may move in, letter case in ids and hidden characters, store reloads after a database import, per-section failure isolation, the button list, and the dialog's keyboard handling). `getExportableSettings` is tested against the store's actual persisted keys, and `SETTING_IMPORTERS` is typed to cover all of them, so a new setting cannot silently be left out of exports.

### Fixed

- SSH and Telnet connections could stay open after the app had stopped showing them, so a remote device went on treating the session as in use: one that allows a single session, or a single configuration session, could then refuse a new one, or changes made from it. russh does not close a connection when its handle is dropped while a channel is still held, and SSH keepalives kept such a connection, and every jump host under it, alive indefinitely. There were five ways to get there:
  - **A session that ended on its own** (the device closed the shell, `exit`, an idle timeout) left its SSH connection and its jump host connections open until the tab was closed. The reader task now disconnects the target and then each jump host as soon as the session ends. Telnet was unaffected, because its I/O task owns the socket.
  - **Reconnecting a disconnected tab** (Enter) never closed the old session, which stayed open until the app quit and counted toward the 100-session cap. A reconnect now closes the old session first and waits until it is closed, so the device has seen it end before the new connection arrives. If the tab is closed while that happens, the reconnect stops there.
  - **Reloading the window** (F5, Ctrl+R) threw away every tab but left all their sessions connected, out of sight and with no way to close them until the app quit. A page load in the main window now closes every session from before it, local shells included. A connect still in flight during the reload is refused when it tries to register, and closed, and one waiting on a host-key or keyboard-interactive prompt that no longer has a dialog ends at once rather than at the prompt's timeout.
  - **A connection refused at the final registration**, because a concurrent connect took the 100th slot, was dropped without stopping its reader task, which kept the channel or socket and with it the whole connection open. It also went on reading output and wrote it to a session log. `SshSession` and `TelnetSession` now stop their reader task when dropped, and a dropped SSH session also disconnects its chain in the background.
  - **After a reconnect, the tab kept the protocol it was opened with.** If the saved session had been changed from SSH to Telnet (or back) in between, the tab sent input to, and closed, the new session with the other protocol's commands, which fail silently, so closing the tab never closed the new connection. The tab now takes the protocol of the session it reconnected to.

  Closing a tab now sends `SSH_MSG_DISCONNECT` to the target and then to each jump host, and waits until they have closed, up to 3 s for the whole chain. A Telnet tab waits for its socket to close, and a local shell tab for the shell to exit. No close holds the session manager's lock while it waits, so a slow server or a stuck shell cannot hold up input to the other tabs. A local shell whose kill fails is no longer waited for, since the wait could block for good, and closing a local shell tab no longer blocks the main thread while the shell exits. An SSH connection that fails after the TCP connection is up (authentication, opening the shell) is now disconnected explicitly rather than left to close once russh notices the dropped handles. So is a jump chain that fails part way (a jump host refusing the login, a tunnel that cannot be opened), down to every hop already connected. Every connection of a chain is held by a guard from the moment it connects until the session is open, so this also holds for a connect that is abandoned part way, and an SSH reader that stops unexpectedly still closes its chain. Covered by tests in `ssh/mod.rs` against an in-process russh server. One shows that a dropped handle leaves the connection open while a task still holds its channel, and that stopping the task closes it. Others check that `SshConnection::close` returns only after the target and the jump host are both closed, that a second close returns at once, and that a jump chain dropped part way disconnects its hops while a finished one does not. Tests in `telnet/mod.rs` check that a refused, removed, dropped or closed session stops its I/O task. `TerminalTabs.test.tsx` covers the reconnect order, a tab closed before or during the reconnect, a failed teardown of the old session, and the protocol carried over. The end of a session on its own and the page-load cleanup need a running app and are not covered by automated tests. Pre-existing.
- **Quitting the app left its SSH and Telnet connections for the operating system to close,** so a device saw the TCP connection end but received no `SSH_MSG_DISCONNECT`. Quitting now closes every session as closing its tab does: each SSH connection, its jump hosts included, is sent `SSH_MSG_DISCONNECT` and waited for, each Telnet socket is closed, each local shell killed and each session log closed and written. The sessions close side by side, each SSH chain giving up after 3 s, and the app exits after 4 s whatever is still closing. While SSH or Telnet sessions close, a **Closing sessions…** notice with a progress bar covers the window, in all 14 languages. It has no buttons, since the quit cannot be called off; it takes the focus from the terminal and keeps every key from the app until it exits.
  - **Every way of quitting closes the sessions first.** Ctrl+Q and the window's close button go through the new `app_quit` command, after the confirmation where the settings ask for one; the window's close button without a confirmation used to close the window, and with it the app, directly. The quit returns at once and closes the sessions on a task of its own, so a second request does nothing, a panic there still ends in the exit, and a connect that finishes while the app quits is refused, as one finishing during a reload is. Should `app_quit` fail, the frontend closes the window as before, and should that fail too, the next quit tries again. Should the app still be running 10 s after the quit began, the frontend closes the window itself.
  - **The menu's quit item** (**File → Exit** on Windows, **Quit ShellStation** with Cmd+Q on macOS; Linux has no such menu) was Tauri's predefined one, which ends the process on the spot with no event the app could hold it on. It is now the app's own, with the same label and shortcut, and quits from the backend directly, so it still works when the webview is hung. Like the predefined item, it does not ask to confirm, since the confirmation lives in the webview; on macOS this includes Cmd+Q, which the menu takes before the webview sees it. The Settings hint that the confirmation applies to Cmd+Q was already wrong before this change and still is.
  - The quit logic moved from `App.tsx` to `src/hooks/useAppQuit.ts`, covered by `useAppQuit.test.ts` (the close button and Ctrl+Q / Cmd+Q, the confirmation and its setting, ended tabs, quitting once, a quit the backend began, the notice, a failed `app_quit`, a failed fallback and the 10 s fallback) and `QuittingOverlay.test.tsx` (focus, keys, no buttons). Two tests in `commands/mod.rs` cover the refused connect and that the quit begins only once. The closing itself is the tab close covered above. The backend's quit task and the menu item need a running app and are not covered by automated tests. The page-load cleanup and the quit now share the code that takes the sessions out of their managers and kills the local shells. The quit confirmation's session count now follows tabs that end while it is open. Pre-existing; found by the pre-commit audit of the connection clean-up fix.
- **A connect sent in the same instant as a window reload could stay connected without a tab.** The backend told the sessions of the old page from those of the new one by a count of page loads, which a connect command read when it started running. A request the old page had already sent could start running after the count went up, and passed for one of the new page. Each page now makes up a token when it loads (`src/page.ts`), announces it with the new `page_announce` command, and passes it as `page` to `pty_spawn`, `ssh_connect`, `telnet_connect` and `session_connect`. The backend opens a session only for the page announced last, so a connect of an earlier page is refused whenever it arrives. It is now refused before it reaches the remote host as well; it used to connect and be closed at registration, which a device still saw as a session.
  - **How the page changes.** A page load closes every session, as before, and leaves no page announced. A token other than the announced one is a new page: its announcement closes every session still there and makes it the announced page. One change is made at a time, and an announcement returns only when the change is complete, local shells included, so a session the page opens after it is never taken by a change still under way. Once the app is quitting, the page no longer changes, since the quit closes the sessions itself. Since every connect now waits for the change of page before it, the change waits at most 2 s for the local shells' lock, which a stuck write to a shell can hold; after that it leaves the old page's local shells running, without a tab, until the next change of page or the quit, so that SSH and Telnet can still connect. The quit waits for that lock as before, within its own 4 s.
  - **In the frontend,** the four connect commands are called only through `invokeConnect`, which announces the page and adds the token, so no call can go out without one; an ESLint rule refuses a direct `invoke` of any of the four. Announcing again changes nothing while the page is the same. The page also announces itself as it starts, so that what an earlier page left behind is closed then rather than at its first connect, and tries once more after a second if that fails. The token is built from `crypto.getRandomValues`, since it is made as the module loads and older WebKit lacks `crypto.randomUUID`.
  - **Two side effects of the count are gone.** A connect the new page started before the count went up was refused, and a local shell it started before the old shells were taken was closed with them. The load is now counted as the webview reports it, and the task that closes the sessions does nothing once the page that load brought has announced itself, since that announcement has closed them.
  - **A local shell that cannot be opened now says so** in a toast, as a failed quick connect does. It used to fail silently, which a refused connect would have as well.
  - **What is left.** An announcement of the old page that is itself on its way during the reload makes it the announced page again until the new page starts, and a second connect it sent in that same moment is then opened. The new page's announcement at startup closes it. Should that announcement of the old page arrive later still, after the new page's, it closes the new page's sessions instead, and the new page's next connect closes what the old page opened.
  - Covered by twelve tests in `commands/mod.rs` (a page load during a connect, a connect of an earlier page before and after the new page's announcement, a connect before any announcement, announcing again, the page-load task running after the new page's announcement, a late announcement of the old page, an announcement waiting for a change under way, a change not waiting for a held shell lock, the quit waiting for it, an abandoned wait taking no shells later, no change once the app is quitting, and the token check), which replace the two for the count; by `src/page.test.ts` (14 tests: each connect command going out after the announcement and with its token, a failed announcement, the token's form and that it needs no `randomUUID`, one token per page load, and the announcement at startup with its retry); and by five tests in `TerminalTabs.test.tsx` (a reconnect, a local shell and a saved session each announcing first and passing the token, and a toast when the announcement or the shell fails). The page load itself needs a running app and is not covered by automated tests. Found by the pre-commit audit of the connection clean-up fix.
- **A session log could be written into a file someone else had put in its place, and was briefly open to others.** A log's name is predictable (session name and minute), and the logger opened it with a call that also opens what is already there, following a symbolic link. Someone able to write to the log directory could therefore have terminal output appended to a file elsewhere. On Unix the file, and a log directory the logger had to create, were restricted to their owner only after they were created, so both could be opened in the moment between. The logger now creates each log with a call that fails when anything holds the name (a file, a directory, or a symbolic link, dangling or not, which is not followed), and as 0600 on Unix as part of that call. A missing log directory is created as 0700 the same way, missing parents included.
  - **A name that is taken is passed over.** The log then gets `_1`, `_2`, … up to `_999` before its extension, as it already did for a name in use, but this is now settled when the file is created rather than when the session connects. Two sessions with the same name that connected in the same minute were both given the same name, since neither had a file yet, and wrote into one file; each now gets its own.
  - **A log whose file cannot be created is given up.** The session goes on without a log and the reason is logged once; the session's tab says so as well (see the entry on the toast, below). The logger used to try again on every output, with a warning each time; with the names now tried one by one, that would also have meant up to a thousand failed creates per output where every name is taken.
  - **Session names that got no log, or an odd one.** A session name with two dots in a row, or ending in a dot before the format's own, was refused as a path traversal, so the session was not logged at all; a name starting with a dot gave a hidden file on Unix; an empty name gave a file called `.log`; and a very long name gave a filename the file system refuses. A dot in a name is now kept only between other characters and never next to another dot, an empty name becomes `session`, and a name is cut at 120 bytes. Found by the review of this change.
  - **What is unchanged.** On Windows a log file got its access list from the log directory, as before, and only the exclusive create applied there; that is fixed by an entry of its own, below. A log directory that already exists is still restricted to its owner afterwards on Unix, as far as it can be. Someone able to write to the log directory can still delete or rename a log, and can keep a session from being logged by taking all thousand names for its minute, which the session's tab now reports (below). Someone able to replace the log directory itself, or a directory above it, with a link still decides where the logs go; the create protects only the log's own name.
  - The checks that compared the resolved path of the log with the log directory, before and after opening it, are gone. The log's name holds no path separator, so the one before compared the log directory with itself; the one after ran once the file was open and could only delete it. The new `create_private_append_file` in `private_fs.rs` shares its create with `create_private_file`. On Windows that create now reports a name held by a directory as already existing, as on Unix, where Windows itself says "access denied".
  - Covered by eight tests in `session_logger.rs` (no file before the first output, a file each for two sessions with the same name, a file or directory already there left alone, a link to an existing file and a dangling one not written through, a log given up when it cannot be created and when all thousand names are taken, the session names above, and the modes of a new log and its directory) and two in `private_fs.rs` (appending after a truncation with a taken name refused, and links not followed). The link tests need the right to create symbolic links, which the Windows machine they were written on lacks, so there they say so and end early; they and the mode test ran on Linux, where both source files' tests pass, and where putting back the plain create, or leaving out the mode, makes the corresponding tests fail. The full Rust suite passes on Windows; the app itself was not started. Pre-existing; found by the pre-commit audit of the connection clean-up fix.
- The connect commands left a session log entry and a terminal-ready signal behind on several early returns: the 100-session cap refusing a connection after the log was opened (`telnet_connect`, `session_connect`), the final registration failing (`ssh_connect`, `telnet_connect`, `session_connect`), a login sequence failing to resolve, and `pty_spawn` failing. A new `ConnectSetup` guard in `commands/mod.rs` opens the log, stores the ready signal and undoes both on every early return, until the command disarms it once the session is registered. It replaces the cleanup each command repeated for a failed connection. The cap is now checked before the log is opened. Closing a tab before its terminal attached also left the ready signal behind; `ssh_disconnect`, `telnet_disconnect` and `pty_kill` now drop it, and close the session log even when the session is already gone. `ssh_connect` and `telnet_connect` now cap the connection timeout (300 s), keepalive interval (3600 s) and keepalive count (100) as `session_connect` already did. Two tests in `commands/mod.rs` cover the guard and its disarming. Pre-existing; found by the pre-commit audit of the Telnet dead-session fix.
- File imports in **Settings** (SecureCRT, mRemoteNG, database JSON, highlight profiles) silently did nothing on Windows: no import, no toast, no log line. The shared file-picker helper treated "window regained focus and no file is present one animation frame later" as a cancel, but in WebView2 the window regains focus as the native dialog closes while the chosen file reaches the page over a separate IPC hop, so `change` routinely arrived after the helper had already resolved `null` and removed its input. Introduced in 0.12.0 with the helper itself. The helper moved to `src/pickFile.ts` and now settles only on the input's own `change` or `cancel` events. For webviews that never dispatch `cancel` (WebKit before Safari 16.4), a pick still pending when the next one starts is settled as cancelled then — the native picker is modal, so it can only be a cancel that went unreported — which bounds the leftover to one hidden element. Covered by `src/pickFile.test.ts`, whose focus-before-change test fails against the old helper with the file resolving as `null`.
- SecureCRT import dropped entity and character references inside element text: a username stored as `dom&amp;user` imported as `domuser`, `&#x2D;` vanished from a hostname. quick-xml reports references as separate `GeneralRef` events between the surrounding text chunks, and `read_text` ignored them. Character references and the five predefined XML entities are now resolved; anything else (undeclared entities, invalid character references) is kept verbatim instead of being lost. Session and folder names were unaffected, since they come from attributes, which quick-xml resolves itself; the mRemoteNG importer reads attributes only and was likewise unaffected.
- Imported usernames now go through the same control-character stripping and 255-character cap as imported names and hostnames. With character references resolved, a reference such as `&#x1b;` could otherwise place a raw control character into a username, which flows into SSH authentication and the `user@host` session log name.
- The import sanitizer (`sanitize_imported_name`) now also drops characters that change how a name _displays_ rather than what it contains, which `char::is_control` does not catch: the bidi embedding, override and isolate controls (U+202A–U+202E, U+2066–U+2069) that can make a crafted hostname or username render as a different one, the line and paragraph separators U+2028/U+2029, and invisible characters with no place in a host, user or session name (U+200B, U+FEFF, soft hyphen U+00AD, U+2060–U+2064, U+FFF9–U+FFFB, and the standalone Hangul fillers U+3164 / U+FFA0). Directional marks (U+200E, U+200F, U+061C) and joiners (U+200C, U+200D) are kept because right-to-left and Indic names and emoji sequences depend on them, and marks cannot reorder text the way overrides can. Applies to imported folder names, session names, hostnames, usernames and jump-host references.
- Import warnings and parse errors are now sanitized before they reach the UI. Parser warnings quote raw file content (`Skipped "<name>" — no hostname`, `unsupported protocol: <value>`, `In "<key>": …`) and quick-xml errors can quote XML fragments, so a crafted export could push control or bidi-override characters into the toasts that display them. Both now go through the same character filter as names, capped at 500 characters each. The number of warnings returned is also capped at 20 plus a final "…and N more warnings" entry: each warning becomes its own toast, and a file full of bad entries previously produced one toast per entry with no limit. The app-log summary line still reports the full warning count.
- The one import error that bypassed this — failing to create the top-level "SecureCRT Import" / "mRemoteNG Import" folder — now goes through the same message sanitizer, and is logged at `warn`. Previously the import aborted with a log that showed it starting and nothing after. The text is a database error rather than file content, so the log line carries it whole.
- SecureCRT and mRemoteNG imports could link a session to the wrong jump host. References were resolved by bare session name with the last session of that name winning, so when two imported sessions shared a name (`bastion` in both `EU` and `US`), every session using that jump host went through whichever came last in the file. A reference that matches several sessions in the file is now left unset with a warning naming the session, and so is a session that names itself. Sessions that were not imported count toward that match — whether the parser dropped them (unsupported protocol, no hostname; both parsers now report these by name and folder) or the import did (invalid port, database error) — so a duplicate that did not make it in cannot leave the other copy looking unique. A reference can also be a folder path ending in the session name (`EU/bastion`), relative to the import root, which picks out one of several sessions that share a name. The index tracks only the references that appear in the file, each with a match count and the first match, and builds paths only up to the 255-character name cap, so its size is bounded by the references rather than by the number of sessions. References are sanitized with one character more than names, so a reference longer than any name can be no longer matches whichever session shares its first 255 characters after both were truncated. The not-found and failed-to-set warnings now name the session they concern.
- SecureCRT import dropped every `<key>` named `Default`, `Default_LocalShell`, `Default_RDP` or `Default_Serial` at any depth, with everything under it and without a warning. The rule is meant for SecureCRT's built-in session templates directly under `Sessions`, and now applies only there, and only to a template's own session settings: the same name inside a folder, or a key of that name directly under `Sessions` that has child keys, is the user's own session or folder and is imported. Two other silent drops, in hand-made or crafted files only — a SecureCRT `<key>` without a `name`, and an mRemoteNG `<Node>` whose `Type` is neither `Container` nor `Connection` — now produce a warning that says how many sessions, if any, went with them, and those sessions count toward jump host ambiguity by name, like other dropped sessions: a reference to `bastion` no longer links `Other/bastion` as if it were unique while a second `bastion` sat in a dropped subtree.
- A SecureCRT or mRemoteNG file cut off part way (an interrupted copy or download) imported everything before the cut without a word, because quick-xml does not report elements still open at the end of the input. Both parsers now fail with "Unexpected end of XML" instead. The SecureCRT parser reads the whole file, since the button bars and the Command Manager come after the sessions (see **Added**), so a file cut off anywhere in it is refused.
- A crafted SecureCRT file could make the import run out of memory. - Saving a newly trusted host key to `known_hosts` had three problems:
  - **Hashed entries stayed.** Accepting a changed key left the old entry in place when it was hashed (`|1|…`), as OpenSSH writes entries with `HashKnownHosts`, the default on Debian and Ubuntu. The new key was then reported as changed on every later connection. Old entries are now found by hashed names too, with `hmac` and `sha1` as new direct dependencies at the versions russh already uses. A line that names other hosts as well, often the host's address, loses only this host's name: the others keep the old key, so connecting by address still reports a changed key rather than a new host. The whole line used to go. A line goes whole when taking the host's name out would leave a name first that makes OpenSSH read it differently, such as a hashed name or `@cert-authority`. Names are read as OpenSSH reads them, and as the new `known_hosts` reader does, except that hashed names are matched more leniently, so that no entry for the host is left behind however it was written. Comments, `@revoked` and `@cert-authority` lines, line endings and lines that are not UTF-8 are kept byte for byte. CRLF line endings used to become LF. A file that was not valid UTF-8 used to keep all its old entries, so once its bad bytes were fixed, the new key was reported as changed in the same way.
  - **The file was rewritten in place.** It was truncated and written again, so a crash part way lost every entry, and a failed write went unnoticed. Taking out the old entries and adding the new one is now a single atomic replace, through the same owner-only helper as `config.json`, and a failure is logged at `warn`. It replaces russh's `learn_known_hosts_path`, and runs off the async runtime. A symbolic link at `~/.ssh/known_hosts`, say into a dotfiles repository, is still followed: the file it points to is replaced, and ends up owner-only, and the link is kept. Of the directories, only `~/.ssh` is restricted, not the one the link points into. A link that points nowhere is an error, and so is anything but a regular file, such as a link to `/dev/null`, which switches `known_hosts` off. In both cases the key is not saved.
  - **Concurrent saves lost keys.** Two connections whose keys were accepted at the same moment could each read the file before the other had written it, and the later write dropped the other key. A lock now covers the read and the write. It covers one running ShellStation, not a second instance or OpenSSH writing at the same moment.

Another user of the machine could otherwise put a file there that trusts their own key for any host. Their access lists must allow no one else to write or append to the file, add files to the directory or remove them, delete or rename either, change their times or other attributes, or change their permissions or owner. The times are part of this since the next entry, on files another user holds or locks. Entries that only deny rights, or only apply to what is created inside, are of no matter, and nor are those for OWNER RIGHTS, which here is an administrator. An entry of a kind the check does not read fails it, as does one too short for the SID it names, and so does having no access list at all, which lets everyone in. The directory must not be a link: a junction, which any user can make, could be pointed elsewhere once checked.     - **Checked through the handle it is read from.** The file is checked through the handle it is then read from, so it cannot be swapped for another between the check and the read. The directory of the file it leads to is not checked, since NixOS links `/etc/ssh/ssh_known_hosts` into `/nix/store`, which a group can write to.

The address's entries never trust a key, a host trusted by name is never asked about because of its address (a different key there is logged at `warn`), and no address is written to `known_hosts`. An entry under the address that cannot be read leaves a new host unchecked. When one under the host's name cannot be read, the prompt says the key could not be checked rather than that only the address is on record, since that entry might be of the key. - On Windows, another user of the machine could have the `@revoked` lines in the system-wide `known_hosts` ignored. Anyone who can read a file can hold it open without sharing it, or lock part of it, and ShellStation then skipped the file with only a `warn` in the log. To use this, a local user had to hold the file while a network attacker presented a revoked key that the victim had already trusted in their own `known_hosts`. Changes:
  - **A locked part no longer stops the read.** When part of a system-wide file is locked, it is read through a read-only mapping instead, which such a lock does not stop. The mapping is copied with `ReadProcessMemory`, so a page that cannot be read, say on an I/O error of the drive, fails the read rather than end the process. A locked file over the 64 MB limit is not mapped. It counts as too large, as an unlocked one does, and leaves the key unchecked; before, the lock made it skipped. The FFI is in `ssh/windows_security.rs`: the declarations of the six functions it calls, and `read_mapped`.
  - **What a file held is remembered.** Each time a system-wide file is read whole, after it and its directory have passed the check that only an administrator can change them, ShellStation stores its `@revoked` lines as `ssh_known_hosts.revoked` and `ssh_known_hosts2.revoked`. They go in `%LOCALAPPDATA%\shellstation`, which a roaming profile does not carry to another machine. A comment line goes first, with the file's size and the times it was created and last written, taken before the read.
    - The stored file is written only when any of that changes. It is kept even when the file has no revocations, so that a file read without any can be told from one never read.
    - Every SSH connection reads the system-wide files, so while a file is there, what is stored follows the administrator's changes. A file that is deleted, or no longer trusted, leaves it as it is, which can only refuse more.
    - Only on Windows, since no other platform lets another user keep a file from being read.
    - Only in the platform's local data directory. When there is none, nothing is stored, rather than in a directory relative to where the app was started, and a `warn` says so.
  - **A held file keeps its revocations.** When another process holds a system-wide file open without sharing it for reading, or has locked part of it and a mapping cannot read it either, the revocations stored from it count.
    - **The file itself is still checked.** It must pass the check that only an administrator can change it, as when it is read. A hold keeps it from being opened to read, so it is checked through a handle that reads no more than its attributes, owner and access list, which a hold does not stop. A file that fails counts for nothing, stored revocations included.
    - **A change since is noticed.** The file's size and times can still be read while it is held. When they are not what was stored, the file has changed and might revoke the key now. The key is then left unchecked, which takes a click, unless a stored revocation already refuses it. A hold that shares writing but not reading lets an administrator's in-place write through, as a manual try with `[IO.File]::WriteAllText` showed, so this is how a revocation added during a hold shows.
    - **Only an administrator may change the times.** Setting them back would hide an edit that keeps the size, such as revoking another key of the same length in place of one. So the check that only an administrator can change a system-wide file, and its directory, now also counts the right to change their times or other attributes. On this machine, `%ProgramData%\ssh` gives SYSTEM and Administrators full control and Authenticated Users read and execute, which still passes, as does Windows' own `hosts` file.
    - **A file never read is skipped,** as before and as OpenSSH skips it, when nothing was stored because ShellStation has never read it whole. Leaving the key unchecked then would let a hold alone put a warning on the connections of every user whose ShellStation has not read the file.
    - When the stored file is there but cannot be read, the key is left unchecked, since it might be revoked. So is a stored file larger than one can be: 64 MB and a kilobyte.
    - Nothing else in the held file counts, as before: a key on record there neither trusts the key nor makes the prompt a warning, so a warning it would have given becomes a first connection's prompt. Only `@revoked` lines are taken from the stored file, whatever else is put there.
    - Within one ShellStation, reading the stored file and replacing it take the same lock. Between two, the replace is a rename, which a read sees whole or not at all.
    - On Windows the stored file is kept from other users by the permissions of the user's own profile, which `%LOCALAPPDATA%` is part of.
  - **Logging**, at `warn` unless said otherwise:
    - A file held by another process is now told apart from one an administrator keeps from the user. The message says that the file is held, and then one of three things:
      - how many stored revocations counted, and whether the file has changed since;
      - that nothing is remembered from it;
      - that what was stored could not be read.
    - A locked part read through a mapping is logged, since nothing should lock the file, and so is a lock that a mapping cannot get past either.
    - Failing to store or to read what is remembered is logged, and so is having no local data directory to store it in, once. Storing it is logged at `debug`.

  - **How.** The stripper went through the output byte by byte. A C1 control is two bytes in UTF-8, and its second byte is one that ordinary characters end in as well (U+009B is C2 9B, `ě` is C4 9B), so it cannot be told from text one byte at a time. The output is now read as UTF-8 first, as the terminal reads it, and stripped character by character. A character that a read ends in the middle of is finished by the next read.

It also means that a device that sends another encoding, such as Latin-1, no longer has its letters beyond ASCII in the log as it sent them, where a viewer set to that encoding could read them: the log shows what the terminal showed. What the stripper hands to the file is now valid UTF-8 throughout; only a write that fails can leave part of a character in the file (see below).
  - **Escape sequences that left their text in the log are removed whole.** An escape with a character between ESC and its last one, or one that ends in a digit or one of `: ; < = > ?`, left those characters behind: `(B` for `ESC ( B`, which many programs send to reset the character set, `7` and `8` for saving and restoring the cursor, `=` and `>` for the keypad modes. The strings DCS, SOS, PM and APC (`ESC P`, `ESC X`, `ESC ^`, `ESC _`) left their text. Both are now read to their end, a string as an OSC sequence is: up to `ESC \`, U+009C or BEL, or a line break or 4096 characters when it has no end. An escape other than `ESC \` that ends a string is read as the escape it is; `ESC ] … ESC [ 31 m` left `31m`. CAN and SUB abort a sequence, as they do in the terminal, where the stripper went on to the sequence's end and took text with it.
  - **What the terminal moves to the next line for is a line feed in the log:** VT, FF, and IND and NEL as `ESC D`, `ESC E`, U+0084 and U+0085. They were dropped, which joined two lines of the session into one; U+0084 and U+0085 went into the log as they came. A control string takes VT and FF with it, as it takes the rest of its text.
  - **A carriage return stays only before a line feed.** In a terminal a CR puts the cursor back at the start of the line, and what follows is written over what the line held, so a host could have a log shown with `cat` display something other than what it holds. A CR that an LF follows is the line break CR LF and is written as such, also with an escape sequence in between. Several CRs in a row count as one, so CR CR LF, which some devices send, is CR LF in the log. A CR before anything else is written as a line feed, so what followed it stands on a line of its own; at the start of a line, where there is nothing to write over, it is dropped. Output that redraws a line, such as a progress bar or a prompt that is edited, therefore takes a line per update in the log, where it used to show as the last state when printed and as one long line in an editor. A pager that clears its prompt with spaces leaves a line of spaces. This was so before the fix and was not part of the issue; it is changed here by decision.
  - **The characters that most often reorder or hide text are dropped,** although they are no control characters: the ones the import drops from a name (the bidi embedding, override and isolate controls, the line and paragraph separators, zero-width space, BOM, soft hyphen, word joiner and invisible operators, interlinear annotation marks and the standalone Hangul fillers), and the tag characters (U+E0000–U+E007F), which can spell out text that is not shown. With an override a host could have a log show a file name or a command as another. Directional marks and joiners stay, as they do in a name: right-to-left and Indic text and emoji sequences need them. A flag emoji made of tag characters loses them. The logger uses the import's own list (`is_display_spoofing_char`). Also so before the fix, and changed here by decision.
  - **What else changes.** A backspace removes a whole character (one code point) from the log; it removed one byte, which left a broken character behind after a letter beyond ASCII. It no longer removes a line break, nor anything after a CR, as the terminal's cursor stops at the start of a line. A control character right after ESC is taken as it is anywhere: a line break there is kept, and a second ESC starts a sequence. A sequence that never ends gives way after 4096 characters rather than bytes, and the application log is told so once for a session, not each time, which a host could repeat at will. After a write to a log that failed, as on a full disk, the next one starts with a line feed: part of the failed one may be in the file, ending in a CR without its LF, which what comes next would be written over, or in the middle of a character. A later entry has the first write that fails end the log, so that nothing comes next and the line feed is gone. If no write follows, the file ends there. A failed write and a failed flush give one warning between them now, not one each.
  - **What is unchanged.** A log holds nothing that a terminal that reads UTF-8 acts on but line breaks and tabs, so showing it there cannot move the cursor back or up, clear the screen or set the title. What it shows can still mislead: a host can always write text that looks like a prompt or like other output, and the list of dropped characters is fixed and not complete. A log is text from a remote host and stays that: stripping it does not make it safe to hand to something that reads markup or runs what it is given. Directional marks, joiners, variation selectors, the combining grapheme joiner and a few fillers that scripts need stay, as they do in a name. A host can choose such characters, and the stripper cannot take them out without taking text out, so a log shown there can still act on the terminal: show a log in a terminal that reads UTF-8 (on Windows, after `chcp 65001`), or open it in an editor. A backspace still removes only what the same output of the session added, since what an earlier one added is in the file already. A character that the session ends in the middle of, and a CR that nothing follows, are not written. BEL ends a DCS, SOS, PM or APC string here, where a terminal reads it as part of the string; what follows is then kept in the log. - **The output of every session waited on one lock while a session log was prepared, created, written, flushed or closed.** A log directory that was slow, such as one on a network share that did not answer, therefore held up the output of all sessions for as long as a write took, those without a log included. The SSH and Telnet readers are tasks of the async runtime, so each one that waited there also kept one of the runtime's threads from everything else. Each log is now written by a thread of its own, and nothing is done to the file system under the lock.
  - **How.** Under the lock, a session's output is stripped as before and handed to the log's writer, which takes no file. The writer makes sure the log directory is there when the session connects, creates the file on the session's first output, and writes: the outputs that are waiting go into one write together, as far as they fit in 64 KiB, and a single output whatever its size. Closing a tab closes its log without waiting; the writer writes what is left, closes the file and ends.
  - **A session waits for its own log, and for no other.** Text that waits for a writer is kept in memory, so it has a limit: 1 MiB for a log, what the writer is at included. ### Changed

- Command bar buttons now read three-digit octal codes for control characters, `\000` to `\037` and `\177`, as SecureCRT's send strings do: `\003` sends Ctrl+C, `\033` ESC. This lets imported SecureCRT buttons keep their commands as written (see **Added**), and gives the command bar every control character, which it could not send before.
  - Codes for printable characters, `\040` to `\176`, are not read and are sent as written. A command spelled in them would show as digits while typing text no one reviewed: `\162\155` would type `rm`.
  - A code above `\177`, an escaped backslash before digits (`\\033`) and fewer than three digits are sent as written too.
  - The free-form input bar reads the codes as a button does, as it already read the other escapes.
  - **A button that sent a backslash and a control character's octal code as text,** such as `printf '\033[1m'` meant for the remote shell's own `printf`, now sends the character instead. Write `\\033` to keep the text.
  - The escape list in the button dialog has a new line for the codes, in all 14 languages.
- The minimum Rust version is now declared: 1.94, as `rust-version` in `src-tauri/Cargo.toml`. It is what sqlx 0.9 needs, the highest minimum the locked dependencies declare, so it has been the real minimum since 0.30.0. Cargo already refused an older toolchain through sqlx's own requirement, and now names ShellStation's. Clippy now knows the minimum too: it flags a standard library API newer than it, and no longer suggests one. `docs/DEVELOPMENT.md` says so as well. How long a path chosen in a backend dialog stays good for saving is written as `Duration::from_mins(10)` again, which needs 1.91. Two lints that clippy 1.95 reports under `just lint` and 1.99 does not are fixed, so that the lint passes on both: the decline cooldown's cap is `Duration::from_hours(1)`, and a doc comment names `SQLite` in backticks. `docs/DESIGN.md` §8 lists sqlx as 0.9+.

It now hands over names, text and entity references as strings rather than bytes, so the tag comparisons in `import/mremoteng.rs` and `import/securecrt.rs` compare strings, and reading text no longer has a decoding step that could fail. Both importers already parse from a string, so the new up-front UTF-8 check changes nothing for them. The release's panic and resource-limit fixes are in namespace handling, the serde deserializer and `Attributes::new`, none of which the importers use. `plist`, through Tauri, still uses 0.41.0, so both versions are in the tree. The existing importer tests pass unchanged.

The standard engine the app encodes with is the scalar one, as before. 0.23 also brings SIMD engines, which the updater plugin's default features compile in; the app does not use them.

- The SecureCRT and mRemoteNG import commands now log at `info` when they start (with the payload size) and finish (folder, session, skipped and warning counts), and at `warn` when parsing fails — as a fixed message, because quick-xml errors can quote fragments of the file (tag names, an unrecognized entity name inside an attribute value); the full error still reaches the UI. Previously an import left no trace in the app log at any level, so an import that never reached the backend was indistinguishable from one that did. No hostnames, usernames or session names are logged.
- The SecureCRT and mRemoteNG imports now reject a file with more than 10,000 folders or 50,000 sessions, the limits the JSON database import already enforced. The 100 MB file cap alone allowed hundreds of thousands of entries, each a database write. The check runs after parsing and before anything is written, so a rejected file leaves no partial import. The two constants in `commands/database.rs` are now `pub(crate)` and shared rather than duplicated.
- Both XML parsers now stop as soon as a file passes 10,000 folders, 50,000 sessions, 50,000 warnings or 50,000 dropped sessions, instead of building every entry before the count check sees them. A 100 MB file holds millions of minimal entries (`<Node Type="Container" Name="f"/>`), and every dropped session or malformed element (a SecureCRT `<string>` without a `name`) collected a warning string, with no limit; a crafted file could make the parse hold several times its own size in memory. Warnings share the session limit because each session dropped on its own produces exactly one. The list of dropped sessions kept for jump host resolution shares it as well, as a count of its own: one warning covers a whole dropped subtree, however many sessions it held.
- The app log level from the config file is now validated before it goes into the log filter. Only ShellStation's own targets get the configured level, so third-party crates such as `sqlx` (which logs SQL statements) and `russh` stay off at every level — but the value was spliced into the filter string unchecked, and a hand-edited `"level": "trace,sqlx=trace"` would have switched them on. It is now lowercased (a hand-edited `"DEBUG"` keeps working, as it always did) and checked against `error`/`warn`/`info`/`debug`/`trace`, falling back to `info` with a message on stderr. The "file logging enabled" startup line now reports the level in effect rather than the raw config value. `RUST_LOG` still overrides the config unvalidated, as a deliberate developer setting; `docs/DEVELOPMENT.md` gained a **Verbose logging** section that says what turning on third-party targets writes to the log file.
- The application log now treats a log directory the user chose as the session logger treats its own, and as it treated the default one already. On Linux and macOS a chosen directory that is already there is restricted to its owner (0700) at each start with application logging on, and a missing one is created as 0700, with any directories above it that are missing too. It used to be created with the default umask, and one already there was left alone. The logging library creates the log file itself, with the mode the umask leaves it, which usually lets every user of the machine read it, so the directory is what keeps the application log from them.
  - **A directory that cannot be restricted** is still used: one that belongs to another user, one on a file system without Unix modes, one the user cannot read, or one with a symbolic link at its name (see below). That is reported on stderr, as it was for the default directory, and now as a warning in the application log itself as well, since stderr is seldom where a user looks; both add that others may be able to read the application log. The log file in such a directory is as open as the umask makes it (see **Known issues**), unlike a session log, which on Unix is created for its owner alone wherever it is (see **Fixed**). The session logger, which said nothing when it could not restrict its directory, now says so for each session, at `info`: others may see the names of the logs there, but cannot open them. That line needs application logging to be on, at `info` or a more verbose level; with it off, nothing records it.
  - **A link at the directory's name is not followed.** Restricting a directory by its path follows a symbolic link there. A log directory can sit where others can write. Someone able to put a link at its name, or to swap one in between the create and the restriction, could have had a directory of the user's elsewhere restricted to 0700, with its setgid bit dropped. Both logs therefore open their directory first, by a call that refuses a link at its name and anything that is not a directory, and restrict it through that handle (`restrict_dir_to_owner_nofollow` in `private_fs.rs`). A separator at the end of the path, which a directory from the config file can have, is dropped first: with one, the system follows a link at the name whatever the call asks. A directory that belongs to another user is refused there as well, which matters when the app runs as root, who could change its mode. This goes for the session logger too, which restricted by path until now, and for the default directory of both logs: only the user can put a link there, but only as long as the config directory around it could be restricted itself. A log directory that is a link the user made is thus no longer restricted where it leads, the default `logs` included, which was until now: the logs still go there, and the application log says so as above. The directory the link leads to can be chosen in Settings instead. A directory the user owns but cannot read cannot be opened and is not restricted; restricting it by path instead would bring the link back. Links above the name are followed as before. The config directory itself is still restricted through a link, so that one kept elsewhere and linked to stays owner-only. The open flags and the user's id come from the `libc` crate, a new direct dependency on Unix that was already in the tree; reading the id is one `unsafe` call, `geteuid`.
  - **Settings says so.** The hints of both log directory fields now add that on Linux and macOS the directory is restricted to the user's account, and that one other users need should not be chosen. Translated into all 14 UI languages.
  - **A log directory with a `..` component can no longer be saved**, for either log: saving now applies the rule that startup applies (`validate_config_path`). Such a path could be saved and was refused at the next start, which then used the default directory for the session logs and switched the application log off. A config file that already holds one, edited by hand or written by a version in which the directory was typed in, now gets that error on saving the log settings until another directory is chosen, as one with a relative path already did.
  - **On Windows** a chosen directory that the app has to create now gets an access list for the user alone, as a session log directory does, and the log file inherits it. A directory on a network share is created the plain way, and one that is already there keeps its list, both as for session logs. On every system, the line that says file logging is enabled, and the new warning, now give the log directory escaped and in quotes, as the start line gives the database host: the directory is whatever the config file holds, and a line break in it must not start a log line. On Windows its backslashes are therefore doubled. The lines on stderr still give the directory as it is.
  - **What it settles.** Whether a chosen directory should be restricted was listed under **Known issues** as undecided, with the two logs doing different things. Both now restrict it: a directory chosen for a log is taken to be for the logs. One that is shared with other users, or holds files others need, should not be chosen, since they lose access to it.
  - Covered in `lib.rs` by checks added to the test for a chosen directory (one that had to be created is its owner's alone, by mode on Unix and by access list on Windows, and no problem is returned), a new test for the default directory, which the code before passed as well, and two new Unix-only tests: a chosen directory that was already there with 0755 is restricted, and a link at the directory's name, for a chosen directory and for the default one, is refused, with the problem returned, the log still written where the link leads and what it leads to left at 0755. In `private_fs.rs` by two new tests (a directory with mode 2775 restricted to 0700 through its handle, also when its path ends in a separator; a link to a directory, the same link with a separator after it, a link to a file, a dangling link and a file at the name all refused, with what the links lead to left at its mode, where the restriction by path goes through the link), and in `commands/logging.rs` by one for the `..` rule. The full Rust suite passes on Windows, and clippy and rustfmt are clean. The whole crate does not build on Linux from here, so `private_fs.rs` and the application log code of `lib.rs`, cut out as it stands with its tests, were built in WSL in a crate of their own: all 15 tests pass there, the Unix-only ones included, and clippy with the pedantic lints is clean. A directory that belongs to another user, running as root, the warning in the application log and the session logger's new line have no test, nothing was tried on macOS, the translations were not checked by native speakers, and the app itself was not started. The link at the directory's name, the separator at its end, the `..` rule, the missing hint, the owner check and the unescaped directory in the log were found by the pre-commit review and audit of this change.

- `cargo audit` still reports advisories that no update can fix yet: `rsa` (RUSTSEC-2023-0071, not reachable from a client, see `Cargo.toml`), which has no fixed version; `glib` 0.18 (unsound `VariantStrIter`) and `proc-macro-error` (unmaintained), both in Tauri's GTK3 stack on Linux, which only a Tauri release can replace; and `zvariant`, `zvariant_derive` and `zbus_names` (unmaintained since their merge into `zbus` 6), through `tauri-plugin-opener`, whose current release still uses `zbus` 5, and through `keyring`'s `secret-service`, which this app's features do not build. Left open after the dependency update under **Fixed**.
- The SecureCRT template rule (see **Fixed**) has not yet been checked against a real SecureCRT export. It assumes a template key directly under `Sessions` has no child keys of its own; if one does, the import gains a folder named after the template.
- A settings import can still set the other settings either way, so a file from someone else can make the app awkward to use: terminal text in the background colour, toasts that close after a second, a UI language the user does not read, a local shell at every start, a refresh interval of 5 s, or the shortest connect timeout and no keepalive. Each shows itself and is undone in Settings, while restricting them would keep a user's own settings from moving to a new machine. Accepted; found by the pre-commit audit of the import direction fix.
- Some quits still leave the SSH and Telnet connections for the operating system to close, with no `SSH_MSG_DISCONNECT` (see **Fixed**), and are not handled yet. One group is quitting from the macOS Dock or at logout, and a system shutdown, which do not go through the app's own quit. The other is installing an update: on Windows the updater plugin exits the process itself, and on macOS and Linux the update dialog's `relaunch()` restarts the app, which Tauri does not let the app hold; the update dialog could close the sessions first. A connection still being set up when the app quits is left to the operating system as well, and so is a session still closing when the 4 s are up, or one that a page load or a new page's announcement took in the instant before the quit began: those are closed in the background, and the quit, finding nothing to close, does not wait for them. Found by the pre-commit audit of the connection clean-up fix.
- On Windows a session log on a network share is still only as private as its directory there. What the app creates on a share gets its access list from the directory above, as before (see **Fixed**), so whoever the share lets read that directory can read what a session showed, passwords echoed by a device included. The same goes for the app's own files when the user's profile is kept on a share. A list of the log's own would have to name the user by a SID the server knows, which it does in a domain but not when it is reached with another account, and the app cannot tell which it is. Naming the owner in the list instead (the OWNER RIGHTS SID) might serve both; it was held back because whatever is later created in a new `.ssh` would inherit that entry, and OpenSSH may refuse a key with an entry it does not know. Kept by decision when the access list was fixed.
- Toasts lie above dialogs, so a stack of them can cover part of a dialog and take the clicks meant for it. In a window less than about 1350px wide, a dialog reaches under the toasts' column with its right part, where its buttons are; the host key prompt is such a dialog. A file from someone else can put up a tall stack with an import's warnings (see **Fixed** for the stack). The dialog can still be used from the keyboard, and with the pointer once the toasts are closed, which **Close all** does, or have closed by themselves. Putting dialogs above the toasts would hide a toast that a dialog itself raises, as Settings does for an error, so it needs a decision of its own. Pre-existing; found by the pre-commit audit of the toast stack fix and deferred to its own change.
- The application log file is not created the way a session log is. The logging library opens whatever holds the day's name (`shellstation.YYYY-MM-DD.log`), following a symbolic link there, and creates a missing file with the mode the umask leaves it on Unix, and with the access list of its directory on Windows. The file is therefore as private as its directory. On Unix other ordinary users cannot get to it by its name once the directory has been restricted to its owner, though a mode takes away neither access that an access control list grants nor a file someone already has open. On Windows they cannot in a directory the app created outside a network share. Elsewhere others may read the application log: on Unix in a directory that could not be restricted (one that belongs to another user, who can read the log in any case, one on a file system without Unix modes, one the user cannot read, one with a link at its name), and on Windows in a directory that was already there and lets others in, the default one of an older install included. Someone able to write to such a directory can also put a link at the next day's name and have the log's lines appended to a file of the user's, or put a FIFO there, which the library's open then waits on: at the start of the app, or at midnight in the thread that writes the log. And should the directory be removed while the app runs, the library creates it again at the next day's file, with the umask's mode and without the restriction. Creating each day's file for its owner alone, refusing a link or anything but a plain file at its name, and keeping the directory as it was made takes a rolling writer of the app's own in place of the library's. Pre-existing; found by the pre-commit audit of the application log directory change (see **Changed**) and deferred to its own change.
- Nothing limits the log directory as a whole. The limits on a session log (see **Fixed**) are for each log by itself: up to 300 sessions can be logged at a time, each with up to 100 MiB by default and up to 12.5 GiB with both limits at their largest, or twice that with files that cannot be deleted, a reconnect begins a new log, and the logs of sessions that have ended are never deleted by the app. Several hosts, or one that the user keeps reconnecting to, can therefore still fill the volume the log directory is on, as a user's own logs can over time. Writes then fail, for the logs and for whatever else writes there; a log is given up at its first write that fails, and its session's tab says so (see **Fixed**). A floor on the free space of the volume, below which a log is given up, would close this. Left out by decision when the limits were added.
- In PostgreSQL mode, not all per-user data is protected by row-level security yet. Details are tracked privately until it is fixed. Pre-existing; found by the pre-commit audit of the shared-row fix and deferred to its own change.
- In PostgreSQL mode, one user can hold database locks that block other users' edits. Details are tracked privately until it is fixed. Pre-existing; found by the same audit and deferred to its own change.
- In PostgreSQL mode, a further gap remains in the protection of shared rows. Details are tracked privately until it is fixed. Pre-existing; found by the same audit and deferred to its own change.
- The PostgreSQL permission model "Option B" promises more than PostgreSQL allows. `docs/ADMIN_GUIDE.md` §2/§5 and `docs/DESIGN.md` §4.5.2 say that under it any user applies migrations automatically. However, `ALTER TABLE` is reserved to a table's owner, which no `GRANT` can confer. So a migration that alters an existing table, like the one that added `owner` and `visibility`, fails for every Option B user but the owner. Option B needs rethinking, for example tables owned by a group role that all users belong to. Pre-existing; found by the review of the shared-row fix and deferred to its own change.
- A first connection's host key is still accepted with Enter, as in OpenSSH's yes/no prompt; only a changed, other-type, address-changed or unchecked key takes a click (see **Fixed**). A man in the middle on a first connection presents exactly such a new key, so an Enter pressed while focus is outside a terminal would trust it. Enter typed into a terminal never reaches the prompt. Kept by decision; found by the pre-commit audit of the host key prompt.
- On Windows, any user of the machine who can read the system-wide `known_hosts` can still hide its revocations from a user whose ShellStation has nothing stored from it (see **Fixed**). That is the case when:
  - the user's ShellStation has never read the file whole, such as for a new user, or
  - nothing could be stored: there is no local data directory, or writing failed, both of which are logged.

  To hide them, a local user holds the file open without sharing it for reading, from before the victim's first connection on. They would also have to do that while a network attacker presents the revoked key, which the victim had already trusted in their own `known_hosts`. For a user whose ShellStation has read the file whole and stored what it read, a hold keeps the revocations last read, and a change since leaves the key unchecked.

  "Unchecked" is a warning, not a refusal. While the file is held after an administrator has changed it, every connection that would not already be refused or warned about warns, first connections and keys the user's own `known_hosts` trusts alike, and accepting takes a click. A user who clicks through accepts a key that the new revocation might name. The hold can keep these warnings up until it ends, for every user of the machine, but only after an administrator's edit, which the hold also keeps every ShellStation from reading. The alternatives would be trusting the key, which would hide the revocation, or refusing every connection, which would let the hold shut users out.

  Three smaller limits remain:
  - **Revocations removed since.** A revocation that an administrator has taken out still refuses its key while the file is held, until it can be read again.
  - **Edits too close together.** Two edits within the same tick of the clock, by default about 16 ms on Windows (not measured here), leave the same last-written time. If ShellStation read the file between them, and the second keeps its size, the second goes unnoticed.
  - **Entries other than revocations.** While the file is held, a key on record in it neither trusts the key nor makes the prompt a warning, as before.

  Rejected alternatives:
  - **Leaving the key unchecked whenever the file is held and nothing is stored.** This would let any user put a warning on the connections of every user whose ShellStation has not read the file.
  - **Keeping the file open while the app runs.** This would stop administrators' `Set-Content` and `move /y` on the file, and would not help a user whose ShellStation has not read it yet.

  Found by the pre-commit audit of the system-wide `known_hosts` change, and narrowed by the fix under **Fixed**.

### Changed

- The terminal cursor no longer disappears against a custom background. Each theme's cursor is an accent color (`#f5e0dc` on dark, `#dc8a78` on light) chosen against that theme's own background, but it was applied verbatim regardless of the **Settings → Terminal → Background color** override — set a light background on the dark theme and the near-white cursor became invisible. `resolveTerminalTheme()` now checks the WCAG contrast ratio between the theme's cursor and the background actually in effect, and substitutes the effective foreground when it falls below 3:1 (the WCAG minimum for a non-text UI element). The cursor then ends up exactly as readable as the text around it. The check only runs when the effective background actually differs from the theme's own, so the accent is left alone whenever it is sitting on the background it was designed for — including the light theme's cursor, which is at 2.3:1 by design and would otherwise have been silently replaced. That comparison is on the resolved color rather than on "is an override set", because the color picker opens pre-filled with the theme default: confirming it unchanged stores an override identical to the default, and that has to behave exactly like no override. `contrastRatio()` returns a non-finite value for a malformed color, and the call site treats that as "no contrast" so bad input degrades to the readable branch instead of throwing.

### Fixed

- **Escape now reaches the terminal again.** In 0.21.0, pressing Escape in any session did nothing — most visibly, vim would not leave insert mode and users had to fall back to Ctrl-C. It also affected `less`, `mc`, and readline vi-mode. Regression introduced by the in-app updater: `UpdateDialog` is mounted permanently at the app root and called `useEscapeKey()` unconditionally (as the rules of hooks require), even though it renders `null` until a check finds an update. That hook registered a document-level capture-phase listener which called `stopPropagation()` on every Escape, so the key never descended to xterm.js and no `\x1b` was ever sent to the remote host. Ctrl-C kept working because the handler only intercepted Escape. Not reproducible on 0.20.x, which predates the updater.
- Escape and Enter ownership is now structurally tied to what a dialog actually renders, which removes the whole class of bug above rather than just the one instance. `useEscapeKey` / `useEnterKey` are replaced by a `<DialogKeys onEscape={…} onEnter={…} />` element that dialogs render inside their own markup (17 call sites converted; both hooks deleted). A claim made in JSX cannot outlive what the component renders, so an invisible component can no longer hold a key hostage application-wide. The failure mode for a dialog that forgets to render it is local and immediately visible — that dialog does not dismiss on Escape — instead of a silent, global loss of a keystroke. `useEnterKey` had the same latent defect and is worse when triggered, since it also calls `preventDefault()`; its four callers happened to be conditionally mounted, so it never fired in practice. Enter still ignores textareas and IME composition.
- Commands sent from the command bar now scroll the target terminal back to the live prompt, matching what typing does. Typed input is handled by xterm.js, which scrolls the viewport to the prompt on keystroke (`scrollOnUserInput`); command buttons and the freeform command bar write straight to the backend over IPC and never pass through xterm, so a user who had scrolled up into the scrollback saw no visible reaction — the command ran, but they had to scroll down manually to see it. Fixed by adding a small `src/terminalRegistry.ts` module that maps session id → live xterm instance (`Terminal.tsx` registers on mount, unregisters on teardown), and calling `scrollTerminalToBottom()` once at the top of `executeCommand` in `CommandBar.tsx`. Putting it there rather than at the four call sites (command button, send-to-all, freeform-to-active, freeform-to-all) means every present and future sender inherits the behavior. Scrolling happens before the first write so the echoed output lands in view, and subsequent output keeps the viewport pinned because it is already at the bottom — including across `\p` pause segments. Send-to-all scrolls every targeted session, not just the visible one, so the other tabs are also at the prompt when the user switches to them. Deliberately not applied to arriving terminal output: yanking the viewport down mid-scrollback whenever the remote host prints something is the behavior scrollback exists to avoid.
- Session sidebar: the previously-selected item is now restored to its visible scroll position after the search input is cleared. Previously, clearing the search caused the tree (which had been replaced by a flat search-results list) to remount with scroll at the top, losing the user's place. A `useEffect` on `searchResults` now detects the filtered→unfiltered transition and queues a scroll request that runs after the tree is committed.
- Session sidebar: deleting a session or folder now reliably scrolls the new selection (the deleted item's parent folder) into view. The previous implementation used `requestAnimationFrame` inside a promise `.then`, which could fire before React had committed the post-`loadAll` render — leaving `scrollIntoView` to target stale DOM. Replaced with a `pendingScrollId` state slot that a `useEffect` consumes on the next render, so the scroll is guaranteed to run against the new tree. The same mechanism replaced four other deferred-scroll sites (folder create/rename and session create/edit), giving a single consistent path for "scroll into view after data settles".
- Highlight-profile rules with regex patterns like `\b(Twe|Hu|Te|Gi|Fa|Fo|Eth)\d+(?:/\d+)*\b` (network interface names) no longer silently fail to apply. The ReDoS safety guard in `src/highlightEngine.ts` was catching the substring `+)*` anywhere in the pattern, but `\d+(?:/\d+)*` is genuinely safe — the `/` literal at the start of the inner group anchors each outer iteration. The heuristic was rebuilt with two complementary checks: (1) single quantified atom inside a group followed by an outer quantifier (catches `(\d+)+`, `(.+)*`, `(a+)*`, `([abc]+)+`), and (2) multiple character-class atoms with no literal anchor inside a group followed by an outer quantifier (catches `(\d+\w+)+`, `(\w+\s+)*`, `(\d*\w*)+`). Groups containing any literal character — `(?:/\d+)*`, `(?:\w+,)+`, `(a+b+)+` — are allowed because the literal acts as an anchor that breaks the inter-iteration backtracking chain. Outer `{n}` (exact count) is no longer flagged as dangerous because a fixed repetition can't create iteration ambiguity. Verified against 18 known cases (10 dangerous, 8 safe); all classify correctly. Also corrected a misleading comment claiming the `try/catch` in `process()` defends against catastrophic backtracking — it doesn't, V8 hangs the thread rather than throwing, so `isSafePattern` is the actual defense. Known residual limitations of the heuristic (not exploitable in the current threat model, which is "user imports a third-party profile; worst case is a tab freeze recoverable by closing the tab"): nested-paren shapes like `((\d)+)+` and `((a|b)c)+` bypass both the nested-quantifier and alternation-quantifier checks; addressing those properly would need a parser-based analyzer or a switch to a linear-time regex engine such as RE2.
- Terminal zoom (Ctrl+/Ctrl-/Ctrl+0) no longer leaves the remote PTY thinking the terminal still has its old cols/rows. Symptom was vim drawing its bottom-right line/column position indicator (and other status content) at the now-out-of-bounds old coordinates after zooming in, with resetting the zoom only moving the artifacts rather than clearing them. Root cause: `effectiveFontSize` changes called `FitAddon.fit()` to recompute the xterm.js grid, but only the container `ResizeObserver` path invoked `ssh_resize`/`telnet_resize`/`pty_resize` — and the container's box dimensions don't change when only the font size changes. Fix: attach a `term.onResize()` listener as the single canonical signal for cols/rows propagation, so any source of `fit()` (container resize, zoom, visibility flip) automatically reaches the backend. Removes a dead `handleResize` `useCallback` that was clearly intended for this wiring but never connected.

- Confirming (or cancelling) the multiline-paste warning dialog now returns keyboard focus to the terminal. Previously the user had to click into the session before typing again: `PasteConfirmDialog` focuses its Cancel button on mount, and when the dialog unmounted that focus fell back to `<body>` with nothing restoring it. Fixed with a rising/falling-edge effect on `pendingPaste` in `src/components/Terminal.tsx` that calls `term.focus()` on the dialog's close transition. The focus call has to happen in an effect rather than inline in the `onConfirm`/`onCancel` handlers, because at the time those handlers run the dialog is still mounted and still holds focus — an inline `focus()` would be undone by the following commit that removes the button. A `visible` guard keeps a background tab from stealing focus, and the edge-tracking ref ensures an unrelated re-render with no dialog open never grabs focus. The paste-confirmation security control itself is untouched: the effect only moves DOM focus and never touches `pendingPaste`, `attemptPaste`, or `term.paste()`.

### Security

- `russh` 0.61.2 → 0.62.4 closes two advisories that are reachable from this app's client role. **GHSA-g9hv-x236-4qp3** (CVSS 5.3): a malicious or man-in-the-middle SSH server replies to key exchange with a short curve25519 ephemeral key, and the missing length check in `compute_shared_secret` panics the client. This fires during KEX — **before** host-key verification — so the known-hosts prompt that would otherwise flag a hostile server never gets the chance to run, and `curve25519-sha256` is in the default set `base_preferred()` keeps. **GHSA-5xvq-cp9x-6p6r** (CVSS 5.3): an all-zero peer public value causes an out-of-bounds panic in `encode_mpint` while computing the exchange hash; primarily a server-role issue, with the client secondarily affected after host-key verification. Both are denial-of-service, not code execution. The host-key path itself is untouched by the upgrade: `russh/src/keys/` is byte-identical between 0.61.2 and 0.62.4, so `check_known_hosts_path` still returns `Err(Error::KeyChanged { line })` and the explicit arm at `ssh/mod.rs:1493` keeps matching rather than falling into its catch-all. `rsa` remains pinned at `=0.10.0-rc.18`, so the RUSTSEC-2023-0071 reasoning documented in `Cargo.toml` is unchanged. Incidentally, `ed25519-dalek` and `curve25519-dalek` graduate from release candidates to 3.0.0 / 5.0.0 stable — these back Ed25519 host-key verification and X25519 key exchange.
- `quick-xml` 0.40.1 → 0.41.0 closes **RUSTSEC-2026-0194** (quadratic run time when checking a start tag for duplicate attribute names), which is genuinely reachable here: both `import/mremoteng.rs:163` and `import/securecrt.rs:433` call `BytesStart::attributes()` with duplicate-checking left on, over XML the user imports from an outside source, so a hostile or malformed `confCons.xml` could hang the import. 0.41.0 makes the check O(N) via a hash pre-filter. The same release covers **RUSTSEC-2026-0195** (unbounded namespace-declaration allocation), which was never reachable from this code — it requires `NsReader`, and both parsers use the plain `Reader`. The advisory-flagged transitive copies (0.38.4 via `plist`, 0.39.2 via `wayland-scanner`) collapse into the same 0.41.0, so the whole tree is on one patched version.
- Lockfile refresh clears the remaining `cargo audit` findings without any manifest change: `rustls-webpki` 0.103.11 → 0.103.13 covers **RUSTSEC-2026-0104** (reachable panic parsing a certificate revocation list), **RUSTSEC-2026-0099** and **RUSTSEC-2026-0098** (name constraints wrongly accepted for wildcard and URI names); `anyhow` 1.0.102 → 1.0.104 covers **RUSTSEC-2026-0190** (`downcast_mut` unsoundness); `rand` 0.8.5 → 0.8.7 covers **RUSTSEC-2026-0097**. None of these were reachable in practice — this app supplies no CRLs to either `reqwest` (updater HTTPS) or `sqlx` (PostgreSQL TLS), no crate in the graph calls `anyhow::Error::downcast_mut`, and `rand`'s `log` feature is off — but they are cleared rather than carried. The yanked `spin` 0.9.8 → 0.9.9, `aes` 0.9.0 → 0.9.2 and `crypto-bigint` 0.7.3 → 0.7.5 go with them; the `crypto-bigint` bump also fixes a real Karatsuba carry-truncation bug.
- A dialog can no longer answer a keystroke meant for the dialog on top of it. Escape/Enter ownership went to whichever modal mounted most recently, but every `.dialog-overlay` shares `z-index: 100`, so what the user actually sees on top is whichever overlay comes last in the document — and those two orders diverge, because dialogs portaled to `document.body` (`ConfirmDialog`, `PasteConfirmDialog`, `UpdateDialog`) always paint above dialogs rendered inline in the app tree. The exploitable case: `HostVerifyDialog` mounts on its own schedule when an SSH host key needs verification, so it could appear _behind_ an already-open modal (say the quit confirmation) and still own Enter — a user confirming the dialog they can see would silently TOFU-accept a host key they never saw, which is precisely the prompt that flags a changed key / possible MITM. Escape would likewise silently reject a connection. `KbdInteractiveDialog` (auth prompt) has the same asynchronous mount. `DialogKeys` now resolves ownership by document order instead: each instance renders a hidden anchor element, and the claim whose anchor comes last in the document — the one painted on top — receives the key. Claims with a detached anchor are skipped, and when nothing claims a key it passes through untouched, since letting a keystroke reach the terminal is always safer than swallowing it. Pre-existing behavior inherited from the `useEscapeKey` / `useEnterKey` stacks, not introduced by the rewrite, but fixed as part of it since the rewrite owns this model. Regression-tested with a portaled claim that mounts before an inline one.
- `ssh_resize` / `telnet_resize` now use a `tokio::sync::watch::Sender<Option<ResizeRequest>>` instead of the previous `mpsc(4)` + `try_send` arrangement. The watch primitive has the correct semantics for this signal: send_replace is infallible (no Tauri command worker can park, no resize can be silently dropped to "full"), the reader task picks up only the most recent value on its next iteration (intermediate values discarded by design), and the channel's `None` initial state means no redundant `window_change` / NAWS round-trip fires at session startup. Replaces the previous Changed-section entry that described the now-superseded `try_send` approach. `pty_resize` is unaffected because it never had a queue — it calls `portable_pty::MasterPty::resize` synchronously under a `std::sync::Mutex`.

  The auditor also flagged the `state.manager.lock().await` immediately preceding the resize send as a residual stall point that could be replaced with `try_lock`. This was rejected: the lock-hold duration is a single `HashMap::get` plus an `Arc::clone` (sub-microsecond), so the stall is theoretical, while `try_lock` would silently drop a single resize whenever any concurrent op (`ssh_write`, `ssh_disconnect`, …) happened to hold the lock at that instant. Since a single zoom action produces exactly one resize IPC with no frontend retry, a dropped resize would reintroduce the visible-UI desync we just fixed.

- `telnet_write` now mirrors `ssh_write` and dispatches the channel send via `tokio::spawn` instead of awaiting it on the Tauri command thread. The bounded capacity-64 write channel could otherwise park workers when the writer task is slow to drain (e.g. a stalled remote network). `try_send` was rejected here because dropping keystrokes silently would be far worse UX than dropping a resize event: a missing `\n` looks like a frozen shell. The detached task pattern lets the IPC return immediately while still preserving every byte the user typed.
- Per-session inflight-writes semaphore added to both `SshSession` and `TelnetSession`. Capped at `MAX_INFLIGHT_WRITES = 64` permits, acquired via `try_acquire_owned` before each spawned write task and released on task drop. This closes a heap-exhaustion DoS vector that the `tokio::spawn` write pattern would otherwise expose: under sustained adversarial load with a stalled writer, the spawn-and-park pattern allowed unbounded task accumulation, each task pinning up to `MAX_WRITE_SIZE` (64 KiB) of user payload. Worst-case held bytes per session are now bounded to two stacking 4 MiB windows (up to 64 spawned tasks each owning a 64 KiB payload, plus up to 64 already-buffered slots in the bounded write channel) ≈ 8 MiB. Across the 100-session cap, ≈ 800 MiB theoretical maximum. The same protection was applied to the pre-existing `ssh_write` path, which had inherited the same theoretical issue. Frontend sees a `"Too many pending writes for this session"` error when the cap is hit — the only path this can fire under realistic use is a runaway / malicious renderer.

### Changed

- Upgraded `tauri` to 2.11.2 and `tauri-build` to 2.6.2.
- Upgraded `serde_json` to 1.0.150.
- Upgraded `tokio` to 1.52.3.
- Upgraded `sqlx` to 0.9. The two consumer-visible changes:
  - `sqlx::query()` (and family) now only accept `&'static str` or `sqlx::AssertSqlSafe<…>` (PR #3723). The twenty dynamic-SQL call sites that build statements with `format!()` — the `UpdateBuilder` consumers, the bulk-edit `IN (?,?,…)` builders, the BFS folder-walk queries, and the keychain-rotation `CREATE DATABASE` path — are now wrapped in `sqlx::AssertSqlSafe(sql.as_str())`. With `SessionColumn` already enforcing that the only non-placeholder dynamic content is a typed column name, each `AssertSqlSafe` is honest by inspection.
  - The Cargo feature `sqlite` is now a meta-feature that pulls in `sqlite-deserialize` / `sqlite-load-extension` / `sqlite-unlock-notify` (PR #3928, SQLite extension loading is now `unsafe`). ShellStation uses none of those APIs, so the feature was switched to `sqlite-bundled` to keep the binary surface minimal.
- Upgraded russh to 0.61. As of russh 0.60.2, SHA-1 MACs (`hmac-sha1`, `hmac-sha1-etm`) are no longer part of `Preferred::DEFAULT.mac`. ShellStation's default (non-legacy) connection path inherits that tightening — these MACs are no longer offered during negotiation when **Legacy algorithms** is off. The Legacy toggle in the session editor remains the escape hatch and is now the **only** way to re-enable SHA-1 MACs. Targets that previously connected on default settings via SHA-1 MAC negotiation (some older Cisco IOS releases, certain industrial switches) will now require enabling the toggle; the existing "no shared algorithm" hint already points users at that setting.
- Moved `ADMIN_GUIDE.md`, `DESIGN.md`, `DEVELOPMENT.md`, and `RELEASING.md` into a dedicated `docs/` folder. Internal cross-references between these documents continue to use plain filenames because they still share a directory; external references in `README.md`, `CLAUDE.md`, and a comment in `src-tauri/src/db/postgres.rs` were updated to point at `docs/`.
- Upgraded `quick-xml` to 0.40.1. `Attribute::unescape_value()` was deprecated in favour of `Attribute::normalized_value(XmlVersion)` (PR #371), and `BytesText::xml_content()` likewise gained a required `XmlVersion` parameter for correct EOL normalization (PR #938). Both importers pass `XmlVersion::Implicit1_0` because both mRemoteNG (`confCons.xml`) and SecureCRT XML exports declare `<?xml version="1.0"?>`. For the two `Attribute::normalized_value` call sites this is behaviour-preserving — `unescape_value()` in 0.39.2 already delegated to XML 1.0 normalization. For the `BytesText::xml_content()` call site in the SecureCRT parser it is a **deliberate semantic change**: the old `xml_content()` was internally aliased to the XML 1.1 path, which also collapses U+0085 (NEL) and U+2028 (LS) to `\n`. XML 1.0 keeps those code points as-is, matching the file's own version declaration. The call site carries a comment explaining the choice. None of the other 0.40 breaking changes apply to ShellStation (no `NsReader`, no `Reader::read_text()`, no namespace `resolve*()` calls).
- Rust backend now passes `clippy::pedantic` clean (`just check`). Most fixes were mechanical (use method references over closures, `map_or`/`let-else` over `match` for one-arm cases, `clone_from` over reassignment, inlined format args, redundant `continue`/`async` removed). Doc comments throughout the backend now backtick identifier-shaped tokens (`snake_case`, `CamelCase`, product names like `PostgreSQL`/`SQLite`/`SecureCRT`/`ShellStation`/`ConPTY`, and protocol abbreviations like `NAWS`/`IAC`/`SB`/`SE`). Crate-level allows are documented in `src-tauri/src/lib.rs` for patterns that are deliberate architectural choices (`option_option` for three-state nullable updates, `cast_*` for already-bounded integer ranges, `too_many_lines` for the documented orchestration entry points, `needless_pass_by_value` for Tauri command convention).

### 0.12.0

### Added

- Visible warning in settings when PostgreSQL SSL mode is set to `disable` (cleartext credentials over the wire) and a softer note for `prefer` (which falls back to cleartext when the server lacks TLS)
- Keyboard activation (Enter/Space) on the shared-folder chevron in the sidebar (a11y)

### Fixed

- Drag-and-drop overlay drifted away from the cursor at non-100% UI scale (regression after the Tauri 2.11 / wry 0.55 upgrade — webview now reports `getBoundingClientRect` and pointer-event coordinates in different units around CSS `zoom`, defeating the previous compensation modifier)
- Search-result rows in the sidebar were skipped by `scrollIntoView` on selection because they lacked the `data-item-id` attribute the lookup queries
- Shared-folder expansion state could persist after the folder disappeared, causing it to re-open expanded when shared sessions reappeared
- "Saved" indicators for session logging, application logging, and user identity stayed visible indefinitely (or could fire `setState` on an unmounted dialog); they now auto-clear after 3 s and cancel cleanly on dialog close
- Hidden `<input type="file">` elements leaked into `document.body` when the user dismissed the highlight, database, or mRemoteNG/SecureCRT import pickers without selecting a file
- `DndContext` was remounting on every folder/session add or delete (count-based key), aborting any in-flight drag
- `addCommandButton`, `updateCommandButton`, `reorderCommandButtons`, and `setToastDismissSeconds` accepted unvalidated input that could bypass the limits enforced on rehydration
- Confirming the SSH host-key verification dialog with Enter on a first-time connection opened the session twice: the dialog listener fired on the bubble phase after the sidebar's tree `onKeyDown` had already re-triggered the connect. `useEnterKey` now listens in the capture phase, uses a stack so only the topmost dialog reacts, and stops propagation before the event reaches background handlers.
- `useEnterKey` / `useEscapeKey` now register a stable ref per hook instance instead of pushing the raw callback onto the stack. The stack only mutates on mount/unmount, eliminating two latent issues: StrictMode's intentional mount → unmount → mount no longer leaves duplicate entries, and unstable callbacks (inline arrow functions in dialog props) no longer churn the stack on every render. The ref is updated in `useLayoutEffect` rather than during render to remain safe under React's concurrent renderer. `useEscapeKey` also moves to the capture phase to match `useEnterKey`, so background tree/list handlers cannot fire before the dialog consumes the keypress (the capture handler still returns early when no dialog is open, so background Escape handlers like `ContextMenu` and `CustomSelect` keep working when no modal is mounted).

### Security

- PostgreSQL password is no longer round-tripped from the OS keychain through Tauri IPC into webview state when opening Settings; the field loads empty and an empty submission preserves the existing keychain entry
- `autoRefreshInterval` requires a minimum of 5 s (or 0 to disable); prevents a tampered persisted value from driving sub-second `session_data_fingerprint` polling against the IPC bridge
- `setLanguage` validates against the bundled-locale allowlist before passing to i18next (defense against attacker-supplied keys reaching i18next's internal resource map via tampered localStorage)
- Command-button rehydration now requires UUID-format ids and validates field shape (length, color regex)

### Removed

- 150% from the UI scale options. A small (~50 px) residual drag-overlay offset remains at exactly that zoom ratio under the new wry webview; 125% is now the maximum. Users with 150% saved are migrated to 125% on load.
